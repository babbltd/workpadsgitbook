**SUI:** SUI-009  
**Kaios source:** `draft_specs/MARKERS-DESIGN.md` draft-spec 2026-05-17

## 1. What Is a Marker

A Marker — also called a **Stone** — is a tamper-evident commitment artifact: a small hardware device or software token that holds a ratified workpads commitment. Markers are the digital equivalent of a signed, sealed physical contract.

Defining properties:

- **Two-party write**: each committed party writes once into the Marker at ratification
- **Write-lock**: after the threshold of parties have written, the Marker becomes read-only (WORM) or enters appendable-tail mode per write mode
- **Universal read**: any compatible reader (NFC phone, BLE device, QR scanner, or the workpads app) can read and verify the Marker at any time
- **Self-contained**: the Marker holds the complete ratified record — no server lookup required to verify or display the commitment terms

Markers are not blockchain tokens and not financial instruments by themselves. They are tamper-evident commitment artifacts.

## 2. Marker Types

### Option A — NFC Tag (preferred for hardware)

Target chip: NTAG213 or NTAG215 (ISO 14443-A)

| Chip | User memory | Use |
|------|------------|-----|
| NTAG213 | 144 bytes | Compact records (minimal agreement, no long text) |
| NTAG215 | 504 bytes | Full agreement records with financial terms |
| NTAG216 | 888 bytes | Multi-party (3–7) agreements |

Cost: $0.10–$0.30 per tag at volume.

Write-once mechanism: NTAG OTP (One-Time Programmable) lock bits in configuration pages. Set LOCK bits after Phase 4 write completes. Locked pages cannot be overwritten — enforced in chip hardware.

Form factors: sticker, card, coin/disc, pendant/keyfob.

### Option B — QR + Software WORM

For non-NFC contexts:
- Marker UID printed as QR code on a physical card
- RATIFIED_FRAME stored on the workpads server under that UID
- Server enforces write-once: after threshold writes, entry is sealed with a timestamp signature
- Any camera-capable phone reads via QR scan

URL: `workpads.me/m/<marker_uid>` — server serves the RATIFIED_FRAME as a pads-v1 record.

### Option C — BLE Beacon (post-MVP)

Bluetooth Low Energy beacon broadcasts Marker UID. Receivers detect and fetch RATIFIED_FRAME from server or local cache. For location-bound commitments (e.g. site entry agreements).

### Option D — Software-only (server-synced)

When neither NFC nor QR printing is available:
- Marker UID is a `did:stone:` DID generated by the app
- Both parties' apps hold a local copy of the RATIFIED_FRAME, signed by both
- Server holds the canonical sealed copy
- Share via: `workpads.me/p#1pm/<b64url(marker_uid)>`

### Option E — Software-only (peer-to-peer, no internet)

For physical proximity without internet:
- Party A generates Marker UID at creation time
- Parties exchange write tokens directly via NFC tap, BLE, or QR scan between devices — no server involved
- Both apps independently verify both write tokens using each party's device key signature
- Both apps assert WRITE_LOCK locally once both slots verified
- Optional deferred sync: either party may sync to server later; `prev_stone_hash` resolves ordering

P2P write exchange:
```
1. Party A: generate Marker UID, write SLOT 0 locally
2. Party A: encode SLOT 0 write token as QR/NFC:
     [marker_uid][slot_index=0][prev_stone_hash=0x00...][write_payload][hmac_8B]
3. Party B: scan/tap → receive Party A's write token → verify HMAC
4. Party B: generate SLOT 1 write token:
     [marker_uid][slot_index=1][prev_stone_hash=SHA256(slot0_payload)[0:8]][write_payload][hmac_8B]
5. Party B: display SLOT 1 token as QR for Party A to scan
6. Party A: receive Party B's token → verify HMAC → assert WRITE_LOCK locally
7. Both devices: Marker is sealed. Sync to server optional.
```

## 3. Ratification Protocol

```
PHASE 1: OFFER
  Worker creates agreement record (pads-v1 frame, ACK_REQUEST=1, UID set)
  Shared as #1pt URL (template-keyed — terms legible only with template)

PHASE 2: REVIEW AND ACCEPTANCE
  Client reviews terms, taps "Accept"
  App creates State Commit reply:
    CHAIN=1, &c=<offer_uid>
    ACK_REQUEST=1
    participants block: IS_SENDER=1
    story: optional acceptance note

PHASE 3: RATIFICATION DETECTION
  Worker's app detects bilateral chain (both parties have a record in chain)
  Agreement status → RATIFIED
  App generates RATIFIED_FRAME

PHASE 4: MARKER WRITE (optional but recommended)
  Worker holds phone to Marker (NFC) or scans Marker QR → initiates write
  App writes RATIFIED_FRAME to Marker SLOT 0
  Client writes acceptance bytes to Marker SLOT 1
  Marker detects threshold met → asserts WRITE_LOCK
  Marker permanently read-only

PHASE 5: ONGOING USE
  Either party reads Marker to view: agreed terms, both identities,
  ratification date, and current status (derived from chain state)
```

## 4. Marker UID — did:stone: Format

```
did:stone:<base32(pubkey_hash[0:12])>

Agreement-derived UID (both parties have a DID):
  did:stone:<base32(SHA256(A_did + B_did + timestamp)[0:12])>

Phone-hash proxy (Party B has no DID):
  did:stone:<base32(SHA256(A_did + SHA256(B_phone_E164) + timestamp)[0:12])>

Example: did:stone:NBSWY3DPEB3W64TMMQ
```

- Encoding: base32 (case-insensitive, QR-efficient, no ambiguous characters)
- Key derivation: `keypair = derive(device_master_secret, context_label_hash)` — same device always produces same Stone UID for same context; recoverable from device master secret
- `did:stone:` method verified available in W3C DID Method Registry as of 2026-05-17
- W3C registration deferred to stage 2 (resolver infrastructure); unregistered use valid at stages 1–2

**Multiple Stones per user:** each operating context (trade identity, vendor, personal, apprenticeship) gets a separate Stone with a separate keypair. Physical NFC Stones issued per context; software Stones available immediately.

## 5. Write Token Wire Format

```
[marker_uid]         variable — did:stone: string as UTF-8, length-prefixed [u8 len]
[slot_index]         1 byte   — which party slot (0, 1, 2…)
[prev_stone_hash]    8 bytes  — SHA256(current Stone contents)[0:8]; all-zero for first write
[write_payload]      variable — the party's ratification bytes
[timestamp]          2 bytes  — COMPACT_TIME uint16 days
[hmac_tag]           8 bytes  — HMAC-SHA256(device_master_key, above fields)[0:8]
```

**Offline write ordering** (when two parties write simultaneously offline):

- Sequential writes: server orders deterministically by `prev_stone_hash` chain
- True collision (same `prev_stone_hash` from simultaneous offline writes): server flags CONFLICT, notifies both parties; common case requires zero human review

## 6. RATIFIED_FRAME Wire Encoding

```
BASE_TEMPLATE = 101 (State Commit)
META2_PRESENT = 1

meta2:
  COMPACT_TIME = 1
  PARTICIPANTS = 1

setup_byte / transaction_byte: present if financial terms included
COMMIT_TYPE = 10   (terms agreed)

field_flags:
  bit 0:  job        — commitment title
  bit 2:  date       — ratification date (COMPACT_TIME)
  bit 11: story      — agreed terms summary (max 60 chars for NTAG213 budget)
  bit 13: ref_number — agreement reference ID

FLAGS3:
  bit 5: uid           — Marker UID (the did:stone: DID)
  bit 0: context_label — short description ("Fence install, 12 Oak St")
  bit 1: tag           — "marker,ratified"

Financial block (if commitment involves payment terms):
  fin_control + customer_amount + due_date

Participants block:
  Participant 0: Party A (offer maker), IS_SENDER=1
  Participant 1: Party B (acceptor), IS_SENDER=0
  (up to 7 parties for multi-party Stones)

Ratification bitmap (FLAGS4 of compound reply):
  bits 0–6: per-party ratification (1=written, 0=pending)
  bit 7: FULLY_RATIFIED

Sub-record structure (compound frame):
  LINE_TYPE=11: Party A's original offer record bytes (verbatim)
  LINE_TYPE=11: Party B's acceptance record bytes (verbatim)
```

### Size budget

```
meta1:          1B
meta2:          1B
setup:          1B  (if financial)
transaction:    1B  (if financial)
field_flags:    2B
story:          2+60 = 62B  (60-char terms summary)
date:           2B
fin_control:    1B  (if financial)
customer_amt:   3B  (if financial)
participants:   1+25+25 = 51B  (two minimal participants)
FLAGS3:         1B
uid:            1+18 = 19B  (did:stone: compact)

Total minimal (no financial): ~79B   ✓ fits NTAG213 (144B)
Total with financial:         ~94B   ✓ fits NTAG213 (144B)
Full record (long names):    ~300B   → needs NTAG215 (504B)
```

## 7. Marker URL Tag

URL scheme: `#1pm/` — pads Marker record.

```
workpads.me/p#1pm/<b64url(marker_uid)>
```

Receiver app:
1. Decodes Marker UID from fragment
2. Fetches RATIFIED_FRAME from server OR reads from NFC tag directly
3. Renders in read-only agreement view
4. Shows WRITE_LOCK status indicator and lifecycle state

The `#1pm/` tag signals: "this is a sealed commitment — render in read-only agreement view, not standard record view."

|-------------|-----------------|-----------------|------------|-------|
| Hardware (NFC) | No | No | ✓ | WORM bits set on-chip; deferred server sync |

| Software (P2P) | No | No | ✓ | Direct device exchange; no server ever required |
| Software (server) | Yes | Yes | ✓ | Real-time server seal; cleanest path |

## 9. Multi-Party Stones

Up to 7 slots per Marker (matches participants block maximum). NTAG216 (888B) recommended for 3+ party Stones.

Overflow beyond 7 parties: chained participant addendum records (minimal Service records, no financial block, chain-linked to main agreement). No codec change needed.

Threshold sealing (template-defined, Party A can override):

```
THRESHOLD_TYPE:   00=unanimous  01=quorum(N-of-M)  10=first-write-seals  11=custom
THRESHOLD_N:      uint8 — minimum writes to seal
THRESHOLD_M:      uint8 — total expected parties
```

Shell display: "2 of 3 required parties have confirmed."

## 10. Lifecycle States

```
UNWRITTEN  → blank Marker, no slots filled
PARTIAL    → one party has written (SLOT 0 filled, SLOT 1 empty)
RATIFIED   → threshold slots filled, WRITE_LOCK asserted
DISPUTED   → RATIFIED but a linked Amendment record has DISPUTE_FLAG=1
FULFILLED  → RATIFIED + linked State Commit shows CHAIN_COMPLETE=1
EXPIRED    → RATIFIED but past expiry_date in the frame
```

The Marker itself carries only the frozen RATIFIED state. All state transitions beyond ratification are inferred from the chain at read time.

## 11. Security Model

**Write authenticity:** each party's write is signed with their device key (HMAC of write content + device ID + timestamp). The Marker stores both signatures. Verification = re-compute both HMACs and confirm they match.

**Tamper evidence:**
- Hardware: NTAG lock bits — physical WORM
- Software: server stores the RATIFIED_FRAME hash at seal time; reads verify against hash
- Combined: hardware + hash + timestamp signature = three independent tamper-evidence layers

**Replay protection:** each Marker UID is generated uniquely at creation time. A replayed write fails because the new UID has no pre-existing slot registration on the server.

**Privacy:** RATIFIED_FRAME on a plain NFC Marker is readable by any NFC-capable device. For sensitive agreements:
- Use `#1pt/` (template-keyed) encoding for the RATIFIED_FRAME
- Hardware: NFC password-protected read via NTAG's 4-byte password feature

## 12. TRIG Integration

A Marker can carry a TRIG program in its RATIFIED_FRAME governing display at read time:

```
Example:
  Reader is Worker (ROLE=01): show full financial detail + terms
  Reader is Client (ROLE=00): show terms + amounts; hide worker_amount
  Reader is neither (ROLE=11): show summary — "This Marker holds a ratified agreement"
```

TRIG on Markers enables privacy-aware display of sensitive terms without multiple versions of the record. See `trig-spec.md` for TRIG wire format.

---

## 13. Stone Transfer

Transfer via chain record only. The Stone itself never changes after ratification. Transfer is recorded as an Amendment or State Commit referencing the original Stone UID via `parent_uid`. Original Stone remains immutable; chain carries transfer history. A new Stone may be created if the transferred agreement requires fresh ratification.

## 14. Production Path

**Phase 1 (software Marker):** no hardware required. Marker UID is a UUID; RATIFIED_FRAME on server + both parties' apps. Write-once enforced by server. Share via URL or QR.

**Phase 2 (NFC sticker):** off-the-shelf NTAG215 stickers (~$0.20 each). Pre-printed with branding and UID QR. App writes via NFC.

**Phase 3 (custom coin):** custom injection-moulded coin with embedded NFC chip. Branded "Marker" — both a functional commitment device and a brand artefact.

**Phase 4 (ecosystem):** sector-specific Markers; readers in public spaces display Marker content when tapped.
